# Conversation RAG Chatbot
https://huggingface.co/spaces/chicknugget/conversation-rag-chatbot

A Retrieval-Augmented Generation (RAG) system that processes multi-turn conversations, detects topic changes, extracts user personas, and answers questions about users via a chatbot interface.

---

## Project Structure

```
.
├── ingest.py          # Parse conversations, generate embeddings, detect topics
├── store.py           # Store messages and embeddings into ChromaDB
├── persona.py         # Extract user persona from conversations
├── query.py           # Retrieval + answer generation
├── chatbot.py         # CLI chatbot interface
├── app.py             # Gradio web interface (hosted on HuggingFace Spaces)
├── messages.pkl       # Cached parsed + embedded messages (couldn't upload due to the big size)
├── breakpoints.pkl    # Cached topic change indices
├── summaries.pkl      # Cached topic summaries
├── personas.pkl       # Cached persona data
└── chroma_db/         # Local ChromaDB vector store
```

## How to Run

### Step 1 — Ingest & embed conversations
```bash
python ingest.py
```
Parses `conversations.csv`, embeds all messages, detects topic breakpoints, and saves `messages.pkl` + `breakpoints.pkl`. Subsequent runs load from cache automatically (no re-embedding).

### Step 2 — Store in ChromaDB
```bash
python store.py
```
Loads cached messages and stores them with their embeddings into a persistent local ChromaDB instance.

### Step 3 — Generate topic summaries
```bash
python ingest.py  # summaries generated at end of ingest pipeline
```
Calls Groq API to summarize each topic segment. Saves progress every 100 topics — safe to interrupt and resume.

### Step 4 — Extract personas
```bash
python persona.py
```
Calls Groq API per conversation to extract habits, personal facts, personality traits, and communication style into structured JSON.

### Step 5 — Run the chatbot
```bash
python chatbot.py
```

## How Topic Detection Works

Messages are processed **in chronological order** across all conversations. Each message is embedded using `sentence-transformers` (`all-MiniLM-L6-v2`).

Topic changes are detected using a **sliding window approach**:
- For each message at position `i`, compute the average embedding of the `N` messages before and after it
- Calculate cosine similarity between the two windows
- If similarity drops below a threshold, mark a topic breakpoint

```
before_window = mean(embeddings[i-4 : i])
after_window  = mean(embeddings[i : i+4])
similarity    = cosine_similarity(before_window, after_window)
if similarity < 0.2 → new topic
```

This is more stable than comparing single consecutive messages, which produces noisy results due to the short nature of chat messages.

Each topic segment gets:
- A `topic_id`
- Start and end message indices
- A 2–3 sentence summary generated by an LLM

## How Retrieval Works

The system uses **two retrieval paths** that are combined at query time:

### 1. Dense retrieval (ChromaDB)
The user query is embedded using the same `all-MiniLM-L6-v2` model. ChromaDB performs approximate nearest-neighbor search over all stored message embeddings and returns the top-K most semantically similar messages.

### 2. Keyword retrieval over topic summaries
Topic summaries are scored by word overlap with the query. The top matching summaries are included as additional context.

Both results are passed as context to the LLM (Groq `llama-3.1-8b-instant`), which generates a grounded answer based only on the retrieved content.

```
query → embed → ChromaDB → top-K message chunks
                                              ↘
                                          LLM → answer
                                              ↗
query → keyword match → top topic summaries
```

## How Persona is Built

For each conversation, a Groq LLM call extracts the following in structured JSON format:

```json
{
  "habits": ["running", "reading"],
  "personal_facts": ["owns a 1964 Impala", "studying radiology"],
  "personality_traits": ["empathetic", "curious"],
  "communication_style": {
    "tone": "friendly",
    "message_length": "medium",
    "emoji_usage": "none",
    "other": ""
  }
}
```

Rules enforced in the prompt:
- All arrays must contain plain strings only
- Only extract what is **explicitly stated** in the conversation — no guessing
- If a field has no evidence, return an empty array

At query time, personas from all conversations are aggregated (deduplicated) into a single context block passed to the LLM.

## Design Decisions

| Decision | Reason |
|---|---|
| `all-MiniLM-L6-v2` for embeddings | Fast, lightweight, runs locally, no API cost |
| ChromaDB for vector store | Local persistent storage, no server setup needed |
| Groq `llama-3.1-8b-instant` for LLM | Free tier, fast inference |
| Sliding window topic detection | More stable than single-message comparison for short chat messages |
| Pickle caching | Avoid re-running expensive embedding/summarization on every run |
| Checkpoint every 100 summaries | Safe resumption if Groq rate limits interrupt the pipeline |

## Limitations & Future Improvements

- Topic summaries and personas currently cover a subset of the full dataset due to Groq API rate limits. The pipeline is designed to resume from any checkpoint.
- Summary retrieval currently uses keyword overlap — replacing this with embedding-based retrieval would improve accuracy.
- Persona aggregation across 56k conversations would benefit from clustering similar traits rather than simple deduplication.
